01Sign up

A single form, then an SMS code. The account exists only after the code is verified.

Page /registerAPIs send-otp → verify-otp → register → referral/apply → profile/photos
  1. Registration status check. If admin closed registration the form shows an alert; if the check fails the form stays open.
  2. Form. Arabic first and last name (other characters stripped as typed), gender cards, phone, optional invitation code (pre-filled from ?invitationCode=), optional photo.
  3. Send code. Server checks maintenance, rate limits (3 per phone / 5 min, 10 per IP / 15 min) and whether the phone exists. Existing phone → redirect to /login?exists=true. Code lives 5 min; a failed SMS deletes it and returns 502. Test numbers get 111111.
  4. Verify + create. verify-otp marks the code verified (5 tries per phone). register creates the User (email phone_962…@naseeb.local, 3 credits, ledger REGISTRATION) and emails the admin.
  5. Auto sign-in, then referral and photo. Sign-in uses up the code. Referral or photo failures show as amber warnings.
  6. Success screen. «ابدأ إعداد ملفك» → setup wizard.
Notifications
Admin email only. The member gets nothing.
Not checked here
  • Age (only in setup)
  • Terms / privacy acceptance

02Sign in & session

Phone + code only. Passwords exist for admins only; forgot / reset password pages just redirect to login.

Page /loginCode lib/auth.ts · auth.config.ts · middleware.ts
  1. Send + verify code. Unknown phones still get an SMS.
  2. signIn. 5 tries per phone per 15 min. Suspended → refused. Deactivated may sign in.
  3. Unknown phone. Phone + code are handed to /register?from=login through sessionStorage.
  4. Success. Always lands on /dashboard.
  5. Session. JWT, 30 days by default, holds id / role / gender. requireUser() re-reads status from the DB; requireAdmin() trusts the token.
  6. Gates. Middleware only checks signed-in and admin role. The dashboard layout shows a suspended screen or the reactivate-only gate.

04Profile edit & review

After setup, most changes go to an admin review queue. Partner preferences and dealbreakers save directly.

Page /dashboard/profile/edit (always 5 steps)APIs profile/update-request · profile/parent-info · profile/dealbreakers
  1. Submit validates steps 1–5. Step 5 is the guardian and requires name, phone, relationship and address.
  2. pref* fields save directly, then a dealbreaker sweep closes cards that no longer fit, then a top-up.
  3. Everything else in steps 1–4 becomes one ProfileUpdateRequest (one pending at a time). The form locks except step 5 until an admin decides.
  4. Admin approves or rejects in Admin → Profile Requests. Member gets a SYSTEM notice; suggestions refresh.
  5. Guardian change saves directly. Withdrawing consent notifies partners on accepted family intros.
Review rule
Filling an empty field or resending the same value is direct; changing or clearing a stored value needs review (reviewedChanges).
Completeness score
Basic 35 · preferences 25 · quiz 15 · photos 15 · family + guardian 10. Not a gate in the new cycle.

05Photos, quiz, referral

Photos

Up to 5 images (JPEG / PNG / WebP, 5 MB, compressed in the browser) uploaded to Bunny under photos/{userId}/ and served from the public CDN. First photo is the main one. There is no blur: photos are simply not sent before a match. After a match the partner's photos are returned unless blocked or inactive. Identity verification and the face-match badge are removed.

Personality quiz

20 Likert questions, all required, no partial save. Builds a 5-dimension vector used for 30% of the score. Retake after 3 months. Refreshes suggestions.

Referral

  1. Code created on first visit to /dashboard/referral; link is /register?invitationCode=….
  2. Apply once, before setup is finished, never your own.
  3. Reward when the new member has finished setup and saved a guardian: referrer +2, new member +1, both notified.

06Suggestions generated

Automatic, no admin. One Suggestion row (flow MUTUAL) is shown to both people.

Engine lib/matching/auto-suggest.ts · score.tsTriggers suggestions page / dashboard load, profile save, quiz, preferences save, after a decision, on expiry, daily job (150 users)
  1. Am I eligible? USER role, not suspended / deactivated / flagged / engaged, setup finished, seen in the last 30 days.
  2. How many slots? 5 − open cards. A card older than 2 days whose other person hasn't been seen for 2 days stops using a slot but stays visible.
  3. Show hidden cards first. Cards created while I was full (hiddenFromCandidate) are revealed best score first, each with a fresh 7 days.
  4. Find candidates. Opposite gender, active, complete, not flagged or engaged, no past pair / match / block, same test group. Both sides' dealbreakers must pass (a missing value fails).
  5. Score ≥ 50. Preferences both ways 50 · personality 30 · profile quality 20 (65 / 0 / 35 without both quizzes).
  6. Create rows. 7-day window. If the candidate already has 5, the row is created hidden from them.
  7. Notify. «اقتراحات توافق جديدة» to me and «اقتراح توافق جديد» to each visible candidate, at most once per person per Amman day.
Card shows
Public profile fields, match %, up to 3 "why matched" reasons from my own preferences. No photos, no guardian, no preferences.
Empty state
pending (5 open) or no_candidates with a link to dealbreakers / preferences.
Admin paths
Hand-pick (5-cap enforced, min score not) and Generate (still legacy rules).

07«مهتم» / «لا»

Each side decides alone. Since 19 Oct the «مهتمون بك» tab shows who already said «مهتم» (notice «شخص أبدى اهتمامه بك», once a day); a «لا» is seen only by someone who had said «مهتم».

UI components/suggestions/mutual-suggestions-view.tsx · interest-dialog.tsxAPI POST /api/suggestions/[id]/decide

«لا»

  1. Card hides at once with a 5-second «تراجع» undo; then sent (also on page close).
  2. Saved as DECLINED. The row closes at once (REJECTED). If the other side had already said «مهتم», their waiting card shows «لم يحصل توافق» (no refund); otherwise their card just disappears (19 Oct).
  3. Slot freed, top-up runs for me only.

«مهتم»

  1. InterestDialog. Pick «محادثة هنا أولاً» (chat) or family. Family without a guardian shows the quick guardian form; family needs the consent tick. Shows «مهتم يستخدم رصيداً واحداً — رصيدك N» and the refund rule.
  2. One transaction: claim the decision, take 1 credit (only if balance ≥ 1), write ledger INTEREST. A double tap charges once.
  3. Balance hits 0 → PAYMENT notice «انتهى رصيدك — اشحن لتتابع».
  4. Card moves to «بانتظار الطرف الآخر» until the window ends, whatever the other side did.
  5. If the card was hidden from the other side, it is revealed to them now with «شخص أبدى اهتمامه بك» and a fresh 7 days.
  6. Other side already «مهتم» → ACCEPTED → mutual match (flow 9).
At 0 credits
Cards stay fully visible, «لا» stays free, «مهتم» is disabled with a recharge link. Cards where the other side said «مهتم» show «أبدى/أبدت اهتمامه بك».
Refund
Only when the window closes and the other side never answered. No refund after a «لا».

11In-app chat

Text only between the two members, filtered, real time through Ably. Admins can read the full history (each view is logged).

Pages /dashboard/chats, /dashboard/chats/[id]Code lib/chat/service.ts · filter.ts · ably.ts
ACTIVE→EXPIRED/ENDED (user or admin)
  1. Send a message. Refused if chat off, expired, ended, a user suspended / inactive, or blocked.
    • Filter: links, emails, @handles, phone digits (all digit scripts), spelled-out numbers, social keywords, a short insult list.
    • Split numbers caught across the sender's own consecutive messages (10 min, 6 back).
    • Limits 5 per 5 s, 50 per day.
  2. Partner pushed (push only, one per 3 min per chat, shows the text).
  3. Day 7: one "ready for a family introduction?" nudge to both while the family path is open.
  4. 2 days left: warning to both. Either side may extend +7 once in the last 3 days; partner told.
  5. Move to family any time: «ننتقل لتعارف عائلي» in the strip or the expired footer, free.
  6. Expiry: read-only; both get «هل تنتقلان لتعارف عائلي؟ الانتقال مجاني». 14 days later with no family request the match counts as finished.
  7. End / end and report: ENDED, pending family requests cancelled, partner told. Ending closes the family path on this match. With a report it also blocks.
Guardian read-only access to the chat was in the design (new-cycle-design.md) but is deferred and not built.

12Family intro & follow-up

The platform shares guardian name, relationship and phone. Families arrange the visit themselves; the site only asks how it went.

  1. Contacts shown on the match card (GuardianContactCard, tel and WhatsApp links). In a mixed match the family-chooser sees an amber "waiting" banner until the other side shares.
  2. Follow-up «كيف يسير التعارف العائلي؟» at day 7, then every 14 days, at most 3 times.
  3. ما زلنا نتعارف (CONTINUING) keeps it open; also the undo for engaged.
  4. لم يحصل نصيب (NOT_A_MATCH) closes the match for both, ends any chat, cancels requests, partner told gently.
  5. تمت الخطبة (ENGAGED) closes my undecided suggestions (with refunds), pauses new ones, asks the partner to confirm.

14Pause, delete, return

  1. Pause (POST /api/profile/deactivate, a toggle). Chats end, pending requests cancelled, chat partners told. Dashboard shows only the reactivate page.
  2. Delete request schedules deletion in 30 days and deactivates. Same clean-up as pause.
  3. Return (POST /api/profile/reactivate) clears the flag and cancels any pending deletion.
  4. Final deletion (daily job): Bunny files removed, open-match partners told, report evidence snapshotted, user deleted.
  5. Support /dashboard/support tickets (max 5 open), admin replies with a status + note. Public /contact form saves a message and emails the admin.

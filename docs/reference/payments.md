# Payments

Stripe flow, checkout page, prices and conversion work. Failure reasons are in admin-panel.md.

> Reference detail moved out of `CLAUDE.md` on 2026-11-06. If this file and `CLAUDE.md` differ, `CLAUDE.md` wins.

## Stripe payments

- Jordan's prices are shown in JOD and charged in **USD**, Saudi Arabia's shown and charged in SAR — one package list per country in `src/lib/payments/packages.ts`, prices set in Admin → Countries (see Money under Countries; the payments page shows the USD amount; owner's choice, Oct 2026).
- Flow: `POST /api/payments/checkout` → embedded Stripe Checkout Session (metadata `app: "naseebak"`, `paymentId`, `userId`, `credits`; expires after `CHECKOUT_TTL_MS` = 35 min) → the PENDING `Payment` row (with `stripeSessionId`) is written only after Stripe returns the session (a Stripe error → 502, logged as `[payments] Stripe checkout session failed`, no row) → credits are added by `fulfilCheckoutSession()` (`src/lib/payments/fulfil.ts`) only when `payment_status === "paid"`, once (claims the Payment row in the same transaction, also a FAILED/timed-out one), from three places: the webhook (`checkout.session.completed` / `async_payment_succeeded`), the return page (`session-status`, owner only) and the daily job (`reconcileStripePayments`, sessions of the last 3 days).
- **The Stripe account is shared with other sites:** anything without our metadata is ignored (`isOurSession`).
- «رجوع» / «إلغاء» (`POST /api/payments/cancel` with `paymentId`) expires the Stripe session and fails the row (credits it instead if it was paid meanwhile); `checkout.session.expired` / `async_payment_failed` fail it too.
- `charge.refunded` (full) → `applyRefund()` (`src/lib/payments/refund.ts`, also used by the admin refund route: REFUNDED once, package credits taken back floored at 0, ledger REFUND, notice in USD); partial refund → admin email only; `charge.dispute.created` → `Payment.disputedAt` + admin email.
- Payment and CreditLedger rows survive account deletion (`userId` set null).
- Webhook events to enable on the naseebak.com endpoint: `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.async_payment_failed`, `checkout.session.expired`, `charge.refunded`, `charge.dispute.created`.
- Lazy-init client in `src/lib/stripe.ts`.
Env vars: `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY`

## Prices per country

- **Money:** package prices are set in Admin → Countries (`country_settings.packagePrices`, by package id; the prices in `src/lib/payments/packages.ts` are defaults) and reach the site, the app (`/api/payments/plans`), checkout and the FAQ within 30 s, with no app version.
  - A package id's credits stay in code on purpose: refunds read them from there, so a different size means a new package id.
  - Jordan's USD charge follows the dinar price at 1.41.
  - **JOD charging (switch `jod_charging`, 2026-11-11, off by default):** new Jordanian checkouts charge `jod` at the dinar price in fils (`chargeFor(price, "JOD", true)` = price × 1000, whole 10 fils; Stripe refuses another last digit). The switch is read once per checkout (`jodChargingFor(country)`, Jordan only) and the row keeps `Payment.chargeCurrency`, so a flip never changes an open checkout; `/pay`, history, refund notices and the admin refund preview read the row (`formatPaidAmount`, `dollarChargeLine`, `refundAmountText`), null = an older row charged in USD. Pro invoice rows take `invoice.currency`: subscriptions started in USD renew in USD. `/api/payments/plans` sends `jodCharging` and drops `chargeUsd`; `chargeLabel` becomes the dinar price, which the app already hides. Admin alerts read Stripe amounts with `fromMinor` (JOD has 1,000 fils). Verified in Stripe test mode 2026-11-11: credits on `/pay` (3.000 JOD, credited), Pro checkouts in JOD, refund, decline, 3DS; payout converts to AED as before.
  - Past payments report their own amount (`formatPaidCharge`), never today's price.
  - Saudi purchases stay off until «Prices approved» is on there (`country_settings.pricesApproved`, null = `PRICES_APPROVED` in code); SAR prices are drafts until then.
  - Checkout `mode: "hosted"` for the app; `GET /api/payments/[id]/status`; local mock checkout (`PAYMENTS_MOCK=true`, `/api/dev/mock-checkout/[id]`) credits through `fulfilCheckoutSession`.

## Pro membership

Code in `src/lib/pro/`. Spec: `docs/superpowers/specs/2026-11-09-pro-membership-design.md`. Not deployed yet.

**Refunds are made only by an admin. Members can cancel renewal; cancelling never refunds.** No code path refunds on its own (owner, 2026-11-09): duplicate subscriptions and renewals paid after Pro ended are cancelled at Stripe and reported to the admins, who refund by hand.

- **Switch and who is Pro:** `pro_enabled` (Admin → Settings, off by default) gates new sales and offers only: checkout (`DISABLED`), `/api/pro` offers and `canBuy`, the Pro page and its links (see below), the chat's greyed media buttons and offer. The badge and media sending follow `isPro()` whatever the switch. `isPro(userId)` = a `ProSubscription` with status `ACTIVE` or `PAST_DUE` and `currentPeriodEnd > now`; it never reads the switch, so subscribers keep Pro.
- **Plans:** weekly, monthly, yearly, per country in `country_settings` (enabled, price, credits per grant; Admin → Countries). Changes reach new subscribers only (`ProSubscription` keeps its own `price` and `creditsPerGrant`). Jordan is shown in JOD and charged in USD cents (`Math.round(price * 141)`), Saudi Arabia in SAR (minimum 2). A sale needs `purchasesAvailable(countrySettings)`, `pro_enabled` and an enabled plan with a price.
- **Where Pro lives** (owner, 2026-11-10): its own page `/dashboard/pro` (`src/app/(ar)/dashboard/pro/page.tsx`): the compact plan card (`ProPlanChooser`) or «اشتراكي» (`MyProCard`, with the past-due note), the Stripe return `?pro=success|cancel` (polls `/api/pro` up to 10 s, `waitForProActivation`) and the local mock panel `?mockPro=<paymentId>`. `/dashboard/payments` has credit packages and history only, plus one small «عضوية Pro» link card (`ProLinkCard`); the card and the «عضوية Pro» entries in the sidebar and «حسابي» show only when `proPageShown` (the member can buy a plan, or is Pro), sent as `pro.showPage` by `/api/me/counts`. Old `?pro=` / `?mockPro=` / `#pro` links on the payments page are sent to the Pro page. Pro notices (started, credits, failed, ended, Pro refund) open `/dashboard/pro` (`PRO_PAGE_PATH`); app 1.0.x maps them to its credits screen by type `PAYMENT`.
- **Checkout:** `POST /api/pro/checkout { plan }` → Stripe Checkout `mode: "subscription"`, inline `price_data` (no dashboard products), returning to `/dashboard/pro?pro=success|cancel`. Metadata on the session and on `subscription_data`: `app` (`CHECKOUT_APP`), `kind: "pro"`, `userId`, `plan`, `country`, `paymentId`, `credits` (the offer's credits per grant: the subscription keeps what the member saw even if the plan changes in the checkout window; older checkouts without it fall back to the plan config). The PENDING `Payment` row (`pro_weekly|pro_monthly|pro_yearly`) is written after Stripe returns the session. A member with Pro, or with a subscription set to cancel, cannot start another. Sessions expire after `CHECKOUT_TTL_MS` (35 min), and starting a Pro checkout first expires the member's other open Pro sessions, so two tabs (or the website and the app) can't both be paid.
- **Webhook** (`src/app/api/payments/webhook/route.ts`, handlers in `stripe-events.ts`, Pro cases before `fulfilCheckoutSession`). Every handler first checks the marker and returns `not_ours` otherwise, because the Stripe account is shared. Events to add on the endpoint: `invoice.paid`, `invoice.payment_failed`, `customer.subscription.updated`, `customer.subscription.deleted`.
  - `checkout.session.completed` (paid, ours): creates the `ProSubscription` and Pro starts, with an estimated period end. Credits wait for the invoice.
  - `invoice.paid`: Payment COMPLETED (`providerTxId` = invoice id), `PAST_DUE` → ACTIVE, period end synced, credits granted. May arrive first; the handler builds the row from the subscription's metadata. A renewal (`billing_reason: subscription_cycle`) never takes the checkout's PENDING row, even if it arrives before the first invoice. «Pro started» is told by the delivery whose grant goes through, so two racing deliveries tell once.
  - `invoice.paid` of a **duplicate** (the member already has a live membership on another subscription): the row is ENDED and never live, the invoice's credits are granted (money was taken), the subscription is cancelled at Stripe at once and the admins are emailed both payments (`lib/pro/duplicate.ts`). Nothing is refunded; an admin refund of that payment takes its credits back.
  - `invoice.paid` on a row already **ENDED or CANCELED** here (a refund whose Stripe cancel failed, or Stripe `unpaid`/`paused` whose open invoice was paid later): Pro does not come back, the credits are granted, the subscription is cancelled at Stripe and the admins are emailed to decide on a refund by hand.
  - `invoice.payment_failed`: `PAST_DUE`, notice to update the card.
  - `customer.subscription.updated`: syncs `cancelAtPeriodEnd`, status, period end (the period moves on only while Stripe is collecting, `active`/`trialing`/`past_due`, and only for a row with a paid invoice: an update before the first `invoice.paid` never makes a duplicate live, and `incomplete` never extends). Status mapping: only `active` (and `trialing`) → ACTIVE and `past_due` → PAST_DUE are live; `unpaid`, `paused`, `canceled` and `incomplete_expired` → CANCELED with `endedAt` and the ended notice. `unpaid` and `paused` are also cancelled at Stripe at once (real subscriptions only; a failure emails the admins), so paying the open invoice later can't restart billing. A local CANCELED or ENDED row never comes back. `.deleted`: `ENDED`, `endedAt`, notice.
  - The handlers read both Stripe payload shapes (before and after API 2025-03-31: invoice `parent.subscription_details`, period on items).
  - `charge.refunded` / `charge.dispute.created` of another site: when the invoice lookup for the charge fails, it is logged and answered 200 as not ours, never 500.
- **Grants:** `grantProCredits` writes a `ProCreditGrant` row (unique `key`), the balance and `recordCredit(..., "PRO_GRANT")` in one transaction, so a re-delivered event or a second run is a no-op. Keys: `invoice:<invoice id>` (weekly, monthly, and month 1 of a yearly year); `yearly:<that year's payment id>:<n>` for months 2 to 12. The morning job (`runYearlyProGrants`) grants each yearly subscription whose `nextCreditGrantAt` is due while it is still Pro, at most 500 per run, then moves it to the next month on the paid year's start day (anchored on the period end, clamped per month: 31 Jan → 28 Feb → 31 Mar, never drifting to the 28th). A new paid year restarts the counter; an older year's invoice delivered late grants its credits without restarting it. A cancelled yearly plan keeps its monthly credits until the paid year ends.
- **Cancel:** «اشتراكي» on the Pro page → Stripe `cancel_at_period_end`; «متابعة الاشتراك» undoes it before the end.
- **Refunds** (admin only: Admin → Payments, or the Stripe dashboard, which reaches us as `charge.refunded`; `applyRefund` knows Pro invoices): a full refund of the current period's invoice ends Pro at once and takes back every credit granted from that invoice (for yearly, all monthly grants of that year), floored at 0, ledger `REFUND`. A full refund of an older invoice takes back only that invoice's grants and Pro carries on. A partial refund only emails the admins. A dispute only flags the payment. Admin «cancel now» and account deletion cancel the subscription in Stripe with no refund and no take-back.
- **Paused or leaving members (2026-11-10/11):** pausing the account, or asking to delete it, stops a live renewal at the period end with a notice, no refund (`stopProRenewalOnLeave`); reactivating never resumes it. If the renewal is already failing (`PAST_DUE`), the pause ends Pro at once so Stripe stops retrying, no refund (WP2-05). A paused member can still read `GET /api/pro` and cancel the renewal (`allowDeactivated`); checkout and resume stay refused, and the page offers nothing to buy (WP2-02). The app shows why Pro stopped renewing, also after a cold start.
- **Notices about money (WP2-03/04/08):** a paid invoice that didn't make Pro live (`Payment.proNotLive`) says the team will refund the duplicate amount (by hand) and carries its credits line, in one notice; a refund of the current period says Pro ended.
- **Legal pages (WP2-01):** the refund policy and the terms have a «عضوية Pro» section (no refund for a period in progress, except a duplicate charge or a payment that didn't activate Pro), shown only while Pro is sold in that country. **The wording waits for the owner's approval (and the open 14-day question) before `pro_enabled` goes on.**
- **Stripe.js** loads through the pure entry and the embedded checkout sits in its own lazy chunk, so pages without a checkout never load Stripe (PA-M3).
- **Local mock** (`PAYMENTS_MOCK=true`): `POST /api/dev/mock-checkout/[id]` with `outcome` `paid` (checkout + first invoice), `renew` (next invoice), `fail` (payment failed), `end` (subscription deleted) runs the real handlers with fake Stripe objects. No Stripe test keys. The owner then makes one real low-price purchase on production.
- **Notices** (all in `src/lib/notifications/automatic.ts`, push + bell, no SMS): Pro started, credits added, payment failed, Pro ended.
- **Chat media:** see "Privacy and domain rules" in `CLAUDE.md`. Upload limits: photo 10 MB in, stored as WebP (long side 1600), HEIC capped at 50 MP and 20 s; voice up to 185 s and 6 MB. Every voice note (MP4 included: Chrome may record Opus in MP4) is transcoded to AAC 64 kb/s in an `.m4a` (`audio/mp4`, `+faststart`, metadata dropped) by `ffmpeg-static` as a child process, one at a time, 30 s timeout. Both queues are capped (HEIC 3, voice 4 waiting or running): more are refused at once with «حاول مرة أخرى», so a burst never waits past the proxy timeout. `GET /api/chats/[id]/media/[messageId]` answers 401 when signed out, 404 to anyone else outside the chat, and keeps the bytes of a file 60 s in memory (32 MB in all, keyed by message id) so a player's Range requests read Bunny once. Account deletion deletes media files after the database transaction (a crash in between leaves files with no row; accepted, since the other order could lose rows' files while the rows stay). The demuxer is pinned from the validated MIME (`-f webm|ogg|mp4|aac|mp3`), the bytes go in on stdin with `-protocol_whitelist pipe` (MP4: `cache,pipe`, to seek back when `moov` follows `mdat`), no shell: content can't pick a playlist demuxer or open files.
- **Deploy notes:** `pnpm install --frozen-lockfile` must run (`heic-convert`, `ffmpeg-static` whose postinstall downloads about 70 MB from github.com, `FFMPEG_PATH` overrides, pinned `sharp@0.34.5`). PM2's cwd is the slot directory (`heic-worker.mjs` via `process.cwd()`). Nginx: `client_max_body_size` ≥ 11m and `proxy_read_timeout` ≥ 120s on `/api/chats/*/media` (jobs queue). Stripe endpoint: the four events above; the owner checks its API version and the Billing "after all retries fail" setting (cancel or mark unpaid: both end Pro here).
